# Minima — поддержка с backend и SMTP

Одностраничная консоль Minima подключена к FastAPI backend. Обращения, изменения статусов и переписка хранятся в SQLite; публичный ответ отправляется клиенту на email по SMTP. Внутренняя заметка сохраняется на сервере и клиенту не отправляется.

Статическая витрина проекта — `docs/`, она публикуется на GitHub Pages. Рабочая консоль с backend запускается на сервере: см. раздел «Развёртывание на сервере».

В консоли есть две роли:

- **Администратор платформы** — учётная запись из `.env`. Видит все обращения, меняет статусы, приоритет и ответственного, отвечает клиентам по почте, оставляет внутренние заметки.
- **Владелец организации** — регистрируется сам с подтверждением почты. Видит только обращения своей организации (совпадение по названию компании), может создать новое обращение; статусы, приоритет, назначение, ответы и внутренние заметки ему недоступны.

> В этой ветке исходный большой прототип из приложенной выжимки отсутствовал. Здесь реализован отдельный раздел «Поддержка», не вся консоль платформы. Разделы «Обзор», «Подписчики», «Платежи», «Тарифы» и «Журнал» не входят в текущую версию.

## Запуск локально

Нужен Python 3.11 или новее.

```bash
cd /home/user/minima
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Откройте `.env` и задайте `ADMIN_PASSWORD` (не менее 12 символов) и `SESSION_SECRET`. Секрет сессии можно сгенерировать так:

```bash
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

После заполнения `.env` запустите сервер:

```bash
cd /home/user/minima
.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Откройте `http://localhost:8000`. Вход администратора — `ADMIN_EMAIL` / `ADMIN_PASSWORD` из `.env`; рядом есть кнопка «Зарегистрировать организацию». OpenAPI-схема доступна по адресу `http://localhost:8000/api/openapi.json`.

HTML, CSS, JavaScript и SVG-иконки остаются в одном `index.html`. Сервер раздаёт этот файл и API с одного origin; CDN и внешние frontend-зависимости не используются.

## Развёртывание на сервере

GitHub Pages не умеет запускать Python: там публикуется только статическая витрина из `docs/` (workflow `.github/workflows/pages.yml`). Сама консоль требует backend — его поднимаем в Docker.

Нужно: сервер с Docker и Docker Compose, домен с HTTPS и доступ к SMTP-серверу провайдера.

### 1. Код и переменные окружения

```bash
git clone https://github.com/dragonslaer666/minima.git
cd minima
cp .env.example .env
nano .env
```

Для продакшена заполните:

```dotenv
APP_ENV=production
SEED_DEMO_DATA=false
COOKIE_SECURE=true
DATABASE_PATH=/app/data/minima-support.sqlite3
ADMIN_EMAIL=support@ваш-домен.ru
ADMIN_PASSWORD=<сгенерируйте длинный пароль>
SESSION_SECRET=<python3 -c 'import secrets; print(secrets.token_hex(32))'>
SMTP_HOST=smtp.провайдера.ru
SMTP_PORT=587
SMTP_USERNAME=почта@ваш-домен.ru
SMTP_PASSWORD=пароль-приложения
SMTP_FROM=Minima Support <support@ваш-домен.ru>
SMTP_REPLY_TO=support@ваш-домен.ru
DEV_LOG_EMAIL_CODES=false
```

`APP_ENV=production` требует `COOKIE_SECURE=true`: без HTTPS браузер не сохранит cookie и вход не сработает. Пароль приложения вводите только в `.env` на сервере — файл в Git не попадает.

### 2. Запуск

```bash
docker compose up -d --build
curl http://<хост>/healthz           # {"status":"ok"}
docker compose logs -f web
docker compose ps
```

Откройте `https://ваш-домен.ru` и войдите администратором. Наружу смотрит только nginx (порт 80), порт backend закрыт внутри docker-сети.

### 3. HTTPS

Получите сертификат (например, `certbot certonly --webroot -w ./deploy/certbot -d ваш-домен.ru`), положите его в `deploy/certs/`, раскомментируйте монтирования в `docker-compose.yml` и блок `443` в `deploy/nginx.conf`, затем `docker compose up -d`.

### 4. Обновление и резервные копии

```bash
git pull
docker compose up -d --build
```

```bash
docker run --rm -v minima-data:/data -v "$PWD":/backup alpine \
  tar czf /backup/minima-data-$(date +%F).tgz -C /data .
```

База — SQLite в томе `minima-data`, это один файл в WAL-режиме; для резервной копии останавливать сервис не обязательно, но желательно. Один экземпляр приложения: PostgreSQL потребуется, если понадобятся несколько реплик.

## Настройка реальной отправки email

Отправка включается только после настройки SMTP. По одному и тому же SMTP уходят и ответы на обращения, и коды подтверждения почты. Заполните в `.env` параметры, выданные вашим почтовым провайдером:

```dotenv
SMTP_HOST=smtp.example.net
SMTP_PORT=587
SMTP_USERNAME=имя-пользователя
SMTP_PASSWORD=пароль-приложения
SMTP_FROM=Minima Support <support@ваш-домен.ru>
SMTP_REPLY_TO=support@ваш-домен.ru
SMTP_STARTTLS=true
SMTP_SSL=false
SMTP_TIMEOUT=12
```

`SMTP_FROM` должен быть разрешённым адресом отправителя у провайдера. Для SMTPS на порту 465 используйте `SMTP_SSL=true` и `SMTP_STARTTLS=false`. Файл `.env` исключён из Git; не вставляйте реальные пароли в исходный код.

### Локальный SMTP-приёмник (сейчас настроен в этой песочнице)

Если под рукой нет доступа к почтовому провайдеру, письма можно принимать локально: backend отправляет их по настоящему SMTP-протоколу, а приёмник складывает в `data/dev-mail/*.eml` и печатает текст в консоль. Наружу при этом ничего не уходит, поэтому адреса вида `*.invalid` и `*.example` безопасны.

```bash
cd /home/user/minima
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python tools/dev_smtp_server.py --host 127.0.0.1 --port 2525 --mail-dir data/dev-mail
```

В `.env` для этого режима:

```dotenv
SMTP_HOST=127.0.0.1
SMTP_PORT=2525
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_FROM=Minima Support <support@minima.local>
SMTP_REPLY_TO=support@minima.local
SMTP_STARTTLS=false
SMTP_SSL=false
DEV_LOG_EMAIL_CODES=false
```

После этого в консоли появляется «SMTP настроен», коды подтверждения и ответы на обращения уходят по SMTP: текст письма видно в логе приёмника, а сам `.eml` — в `data/dev-mail/`. Это проверка всей цепочки отправки, но не доставки в реальный почтовый ящик: писем наружу нет.

### Переход на почтового провайдера

Замените в `.env` пять-шесть строк значениями провайдера и перезапустите backend. Типичные значения (уточните в документации своего провайдера):

| Провайдер | `SMTP_HOST` | `SMTP_PORT` | Шифрование |
|---|---|---|---|
| Gmail | `smtp.gmail.com` | `587` | `SMTP_STARTTLS=true` |
| Яндекс Почта | `smtp.yandex.ru` | `465` | `SMTP_SSL=true` |
| Mail.ru | `smtp.mail.ru` | `465` | `SMTP_SSL=true` |
| Свой домен у хостера | из панели хостера | `587` или `465` | `STARTTLS` для 587, `SSL` для 465 |

Пароль приложения (не основной пароль почты) впишите в `.env` сами: файл исключён из Git и в чат его передавать не нужно. Адрес `SMTP_FROM` должен принадлежать вашему домену и быть разрешён у провайдера, иначе сервер отвергнет письмо — backend вернёт `502` и пометит сообщение как «Не отправлено».

Пока SMTP не настроен, интерфейс показывает статус «SMTP не настроен», блокирует публичную отправку и **не даёт зарегистрироваться**: сервер вернёт `503` и не создаст код, поэтому письмо с кодом не может прийти. Заметки команды при этом продолжают сохраняться. Чтобы безопасно проверить доставку, создайте обращение с адресом своего тестового ящика и ответьте на него. Адреса в начальных демо-обращениях используют зарезервированные домены `.invalid` и `.example` и не предназначены для реальной доставки.

Успешная отправка означает, что SMTP-сервер принял письмо; подтверждение доставки в почтовый ящик не запрашивается. Ошибка SMTP сохраняется в истории как «Не отправлено», не останавливает таймер первого ответа и возвращается оператору. Для повторной попытки отправьте сообщение ещё раз: API использует `Idempotency-Key`, чтобы повтор HTTP-запроса не отправил одно письмо дважды.

## Регистрация владельца организации

Сценарий полностью серверный: код создаёт и отправляет backend, из браузера письма не уходят.

1. В форме регистрации укажите название организации, имя, рабочую почту и пароль (не короче `PASSWORD_MIN_LENGTH`, нужны буквы и цифры).
2. Backend проверяет данные, создаёт одноразовый код и отправляет его на указанную почту через SMTP. Учётная запись на этом шаге **не создаётся**.
3. Введите код в консоли. После проверки создаётся учётная запись владельца и сразу выдаётся сессия.
4. Если письмо не пришло, кнопка «Отправить код повторно» станет доступна через `EMAIL_CODE_RESEND_COOLDOWN_SECONDS` секунд; новый код делает предыдущий недействительным.

Как код защищён:

- В базе хранится только `pbkdf2_hmac`-хеш кода с отдельной солью на каждый код; сам код в базе и в ответах API не появляется.
- Срок действия — `EMAIL_CODE_TTL_MINUTES` минут; код одноразовый и помечается использованным при подтверждении, истечении или исчерпании попыток.
- Не более `EMAIL_CODE_MAX_ATTEMPTS` попыток ввода на один код, дальше код аннулируется.
- Ограничения частоты: не более `EMAIL_CODE_MAX_PER_EMAIL_HOUR` кодов на почту и `EMAIL_CODE_MAX_PER_IP_HOUR` на IP-адрес в час, плюс пауза между отправками и лимит `CONFIRM_MAX_PER_IP_HOUR` на попытки подтверждения.
- Пароль хранится как `pbkdf2_sha256` с солью и привязкой к `SESSION_SECRET`.
- Регистрацию можно закрыть: `SIGNUP_ENABLED=false` скрывает форму и даёт `404` на все три endpoint'а.

Локальная разработка без SMTP:

```dotenv
DEV_LOG_EMAIL_CODES=true
```

В этом режиме backend не отправляет письмо, а печатает код в лог сервера (уровень `WARNING`, логгер `minima.support`) и отвечает `delivery: "server-log"`; интерфейс прямо сообщает, что письмо не отправлено. В `APP_ENV=production` этот режим запрещён — сервер не запустится.

Проверить письмо можно только после настройки SMTP: в тестах SMTP подменяется, настоящие письма наружу не уходят.

## Что сохраняет backend

- Обращения, компанию, контакт, email, тариф, приоритет, статус и ответственного.
- Первое сообщение, ответы команды, внутренние заметки и системные события.
- Сроки SLA, время первого ответа, закрытие и версию записи.
- Статус SMTP-отправки (`pending`, `sent`, `failed`) и сессии администратора.
- Подтверждённые учётные записи владельцев организаций, одноразовые коды подтверждения (в виде хеша) и счётчики ограничений.

База по умолчанию: `/home/user/minima/data/minima-support.sqlite3` (SQLite в WAL-режиме). Для резервного копирования останавливайте сервер и копируйте файл базы вместе с возможными WAL-файлами. Это надёжный односерверный вариант для прототипа/небольшой установки, но не кластерная БД; для нескольких экземпляров сервера потребуется PostgreSQL.

При `APP_ENV=development` новые установки заполняются шестью демо-обращениями с безопасными адресами. Для production установите `APP_ENV=production`, `SEED_DEMO_DATA=false`, `COOKIE_SECURE=true`, используйте HTTPS и сильные уникальные значения `ADMIN_PASSWORD` и `SESSION_SECRET`.

## API

Рабочие endpoints требуют авторизованную сессию, кроме проверки сессии, входа и регистрации. Эндпоинты изменения обращений доступны только администратору: владелец организации получит `403`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/auth/session` | Проверить сессию, роль, состояние SMTP и доступность регистрации |
| `POST /api/v1/auth/login` | Войти администратором или владельцем организации; выдаётся HttpOnly cookie с ограниченным сроком |
| `POST /api/v1/auth/logout` | Отозвать сессию |
| `POST /api/v1/auth/register/request` | Начать регистрацию владельца: проверить данные и отправить код на почту |
| `POST /api/v1/auth/register/resend` | Отправить новый код для начатой регистрации |
| `POST /api/v1/auth/register/confirm` | Подтвердить код, создать учётную запись и выдать сессию |
| `GET /api/v1/support/tickets` | Получить очередь и переписку (для владельца — только его организация) |
| `GET /api/v1/support/tickets/{id}` | Получить одно обращение |
| `POST /api/v1/support/tickets` | Создать обращение и запустить SLA |
| `PATCH /api/v1/support/tickets/{id}` | Изменить статус, приоритет или ответственного (администратор) |
| `POST /api/v1/support/tickets/{id}/messages` | Сохранить заметку либо отправить ответ по SMTP (администратор) |

Вход ограничен после пяти неверных попыток за 15 минут с одного IP и после десяти — для одной почты. Сессии хранятся на сервере в виде HMAC-хеша; cookie — `HttpOnly`, `SameSite=Strict` и в production `Secure`. Межсайтовые запросы отклоняются; CORS не включён. Пароли, коды подтверждения, SMTP-ответы и тело письма не попадают в application logs (код попадает в лог только в режиме `DEV_LOG_EMAIL_CODES`).

## Текущие ограничения

- Администратор платформы по-прежнему один и задаётся через `.env`: регистрация создаёт только владельцев организаций, приглашение сотрудников и управление ролями внутри организации не реализованы.
- Привязка владельца к организации идёт по названию компании: владелец видит обращения, у которых поле «Компания» совпадает с его организацией. Отдельного поля `organization_id` в схеме обращений пока нет.
- Регистрация возможна только при настроенном SMTP (либо в режиме `DEV_LOG_EMAIL_CODES`). Без SMTP сервер честно отвечает `503` и не создаёт код.
- Локальный приёмник `tools/dev_smtp_server.py` — только для разработки: он принимает письма на `127.0.0.1`, не ретранслирует их наружу и не проверяет SPF/DKIM/DMARC. Реальная доставка проверяется только с настоящим провайдером.
- GitHub Pages обслуживает только статику: витрина в `docs/` работает без backend, а консоль с очередью, SLA, регистрацией и письмами — только там, где запущен контейнер с FastAPI.
- Endpoint запроса кода отвечает `409`, если почта уже подтверждена, — это раскрывает факт регистрации почты в Minima.
- Реализована исходящая почта по SMTP. Входящие письма, Telegram-бот, вебхуки и автоматические фоновые SLA-эскалации не подключены.
- Демо-обращения показывают работу интерфейса; для реального обслуживания нужны данные клиентов или входящий канал обращений.
- Подтверждение доставки письма и автоматические повторы SMTP не реализованы; неудачная отправка сохраняется для ручной повторной попытки.

## Проверка

Установите dev-зависимости и запустите тесты:

```bash
cd /home/user/minima
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Отдельно:

```bash
.venv/bin/python -m pytest tests/test_api.py -q
.venv/bin/python -m pytest tests/test_signup.py -q
.venv/bin/python -m pytest tests/test_mailer.py -q
```

Проверить отправку целиком, не трогая реальную почту:

```bash
.venv/bin/python tools/dev_smtp_server.py --host 127.0.0.1 --port 2525   # отдельный терминал
.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000      # отдельный терминал
```

Затем в консоли зарегистрируйте организацию (код придёт в приёмник) или отправьте ответ по обращению с адресом `*.invalid`, и посмотрите письмо в логе приёмника.

Тесты покрывают вход администратора и владельца, ограничения доступа и ролей, создание/изменение обращений, SLA, идемпотентность, сохранение заметок, успешную и неуспешную SMTP-отправку, а также регистрацию: отправку и подтверждение кода, хранение хеша, срок действия, одноразовость, лимит попыток, паузу между отправками, ограничение частоты, отсутствие учётной записи до подтверждения, отказ без SMTP и режим `DEV_LOG_EMAIL_CODES`. SMTP в тестах подменяется; реальные письма не отправляются.
